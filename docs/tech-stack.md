# Tech stack

The stack follows what is common in New Zealand job listings for TypeScript and Node.js roles:
React, Next.js, PostgreSQL, Docker and CI. The application is a single Next.js project that runs
locally in Docker; there is no cloud deployment or authentication.

| Layer              | Choice                                                                       | Notes                                                                             |
| ------------------ | ---------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| Language           | TypeScript (strict)                                                          |                                                                                   |
| Framework          | Next.js (App Router), full stack                                             | Server Actions and Route Handlers; no separate backend                            |
| UI                 | React, Tailwind CSS, shadcn/ui                                               |                                                                                   |
| Forms & validation | React Hook Form, Zod                                                         | One Zod schema shared by client and server (`src/lib/schemas`)                    |
| Database           | PostgreSQL, Prisma                                                           | Runs through docker compose                                                       |
| PDF                | HTML template (React component) rendered to PDF with Playwright and Chromium | Preview and PDF share one template; rendered on demand in a Route Handler         |
| Tests              | Vitest, Playwright E2E                                                       |                                                                                   |
| Tooling            | npm, ESLint, Prettier, GitHub Actions (lint, typecheck, test, build)         | CI only; GitHub Actions is currently switched off, so `npm run check` is the gate |
| Containers         | Dockerfile (Next.js standalone output plus Chromium), docker compose         | `docker compose up` starts the web app and PostgreSQL                             |

## Decisions

- **Next.js only.** A separate NestJS API was considered and dropped for now; Server Actions and
  Route Handlers are enough. The API can be split out later if needed.
- **npm instead of pnpm.** It is a single project and pnpm is not installed on the development
  machine.
- **HTML to PDF with Playwright.** `@react-pdf/renderer` is lighter, but supports only a subset of
  layout and cannot share CSS with the on-screen preview. Playwright gives full CSS, which matters
  for building several templates, at the cost of shipping Chromium in the container.
- **Content snapshots in PostgreSQL.** Saved invoices store their full content, so later changes to
  templates, sellers or customers never alter past invoices. PDF files themselves are not stored.
- **Prisma 7 with the `pg` driver adapter.** The client is generated into `src/generated/prisma`
  (git-ignored, regenerated by `postinstall`). Configuration lives in `prisma.config.ts`.
- **PostgreSQL on host port 5433**, bound to localhost, so it does not clash with a database
  already using 5432. A second database, `invoicer_test`, is created on first start for the
  integration tests.
- **Snapshot as JSON plus summary columns.** `invoices.content` holds the full validated invoice;
  number, buyer name, issue date, currency and total are copied into columns for the list page.
  There are no foreign keys to customers or sellers, which is what makes snapshots
  independent.
- **Design lives in the snapshot.** `template`, `accentColor` and `font` are fields of the invoice
  schema (so the PDF endpoint needs only the invoice), with ids defined once in `src/lib/design.ts`.
  Accent and font are optional: when absent each template falls back to its own default
  (`defaultAccent`, `defaultFont` in the registry).
  The accent colour is written into CSS, so the schema accepts only `#RRGGBB`.
- **Templates share a view model.** `src/templates/view.ts` works out which lines appear and every
  amount as text; each template only decides layout and CSS. Templates scope their styles under
  their own root class and read the colour from a `--accent` CSS variable.
- **Bold and Sky are modelled on two free third-party invoice templates.** Only the layout idea was
  reproduced, in our own CSS and with our own data fields. No logo, text, font file or other asset
  from them is used, and the original PDFs are not part of the repository.
- **Status is stored as draft, sent or paid; overdue is derived.** `effectiveStatus()` combines the
  stored status, the due date and today's date in Auckland. The due date is copied into its own
  column, as an ISO string, so the list can filter overdue invoices in SQL.
- **Money is stored as `BigInt` cents** and calculated with BigInt multiplication. The schema limits
  quantity (100,000) and unit price ($1,000,000) so every total stays inside the safe integer range.
- **No logo upload.** This removes file storage and upload handling entirely.
- **No authentication.** The app is single-user and local; it binds to `localhost` only.

- **PDF endpoint is a Pages Router API route.** Rendering the template to HTML needs
  `react-dom/server`, which Next.js does not allow in App Router route handlers (they run in the
  React Server Components layer). `src/pages/api/pdf.ts` is therefore a Pages Router API route; both
  routers coexist in one project. The alternative, a print page that Chromium navigates to, needs
  JavaScript and network access in the PDF browser and was rejected as more fragile.
- **Chromium is launched per request.** Simple and isolated; it can be replaced by a shared browser
  instance later if PDF latency matters.

## Layout

```
src/app/            pages and layouts (App Router)
src/pages/api/      PDF endpoint (Pages Router, see Decisions)
src/components/     form, preview and other UI
src/templates/      invoice templates (React components)
src/lib/            Zod schemas, money and GST calculation, formatting, PDF rendering
src/server/         database access: Prisma client and the invoice, customer and seller stores
prisma/             schema and migrations
Dockerfile, docker-compose.yml
```

## Containers and testing

- **Image.** `Dockerfile` has four stages: `deps` (npm ci, which also generates the Prisma client),
  `builder` (next build), `migrate` (the Prisma CLI, run once to apply migrations) and `runner` (the
  app). The runner is `node:22-bookworm-slim` plus Chromium from the same Playwright version the app
  was built with, installed before the app code so that large layer is cached. It runs as the
  `node` user and is about 2 GB, almost all of it Chromium and its system libraries.
- **Compose.** `db`, then `migrate` (exits when done), then `web`, each waiting on the previous one.
  `web` has a health check on `/api/health`. Ports are published on 127.0.0.1 only, because the app
  has no login.
- **Fonts in the image.** Chromium picks the Liberation fonts (metric-compatible with Arial, Times
  New Roman and Courier New), which is why the font stacks in `src/lib/design.ts` end with them.
  I checked the PDFs generated inside the container: they embed LiberationSans, LiberationSerif and
  LiberationMono.
- **Chromium without its sandbox in the image.** Docker's default security profile blocks the user
  namespaces Chromium's sandbox needs, so the image sets `CHROMIUM_NO_SANDBOX=1`. The rendered page
  is the app's own escaped HTML with scripts and network disabled, and the container is the
  isolation. Outside Docker the sandbox stays on.
- **The build needs no database and no network.** Pages that read the database call
  `await connection()`, so Next.js renders them per request instead of at build time; the Geist
  font from Google Fonts was dropped for system fonts. Both were found because the first image build
  failed.
- **Three kinds of test.** Unit tests (Vitest) need nothing. Integration tests run the stores
  against a real `invoicer_test` PostgreSQL. End-to-end tests (Playwright Test) drive the production
  build in a real browser against the same test database; they build into `.next-e2e` so they never
  disturb a running dev server. `npm run check` runs all three, plus lint, types, formatting and the
  build. Both database-backed kinds refuse to run unless the database name ends in `_test`.
- **GitHub Actions** is configured in `.github/workflows/ci.yml` (formats, lints, type-checks, runs
  the unit and integration tests and the build) but is currently switched off, so `npm run check` is
  the gate.

## Known notes

- `npm audit` reports high-severity findings in the `eslint-config-next` dev dependency chain
  (`braces`). They do not reach the runtime. The suggested fix downgrades `eslint-config-next` to
  v14, which does not match Next.js 16, so it is deferred until upstream updates.
